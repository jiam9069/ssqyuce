## 2. P0 缺陷

### P0-1 `/api/predict` 写端点不校验 CSRF（enforce 下无 token 仍 200 并写库）

**位置**：`lottery/routes_predict.py:356` `@router.api_route("/api/predict", methods=["GET","POST"])` → `predict()` 函数（无 `_csrf_ok` ／无 `require_csrf` 调用）。对照 `lottery/user_llm_api.py:190` 的写端点是会校验的。

**最小复现**（`qa-tools/qa_audit_csrf_probe3.py`，隔离环境，`LOTT_AUTH_MODE=enforce`）：

```python
from fastapi.testclient import TestClient
from lottery import config, api_app, auth, db
config.AUTH_MODE = "enforce"; config.SESSION_COOKIE_SECURE = False
db.close(); db.get_conn()   # 触发迁移；把 bootstrap 升级成 admin 并建 alice
# ... 建 alice、seed 700 期 draws ...
C = TestClient(api_app.app)
C.post("/api/auth/login", json={"username": "alice", "password": "..."})  # 已登录
print("wrong csrf:", C.post("/api/predict", headers={"X-CSRF-Token": "WRONG"}).status_code)
print("no csrf:",    C.post("/api/predict").status_code)               # 不带任何 CSRF 头
print("control  :",  C.post("/api/user/llm/config", json={"model":"x"}).status_code)  # 对照写端点
```

**实际响应**：

```
== predict WITHOUT CSRF (should 403) ==
wrong csrf: 200 {"issue":"2026122","requested_tickets":5,"actual_tickets":5,...}
no csrf:    200 {"issue":"2026122","tickets":[{"user_id":16,...}]}
== POST user/llm CSRF behavior (control) ==
no csrf: 403 {"ok":false,"error":"CSRF 校验失败"}
good csrf: 200 {"ok":true,"user_id":16,...}
```

**期望响应**：`/api/predict` 的 POST（以及任何会 `regenerate`/写 `predictions` 表的分支）在缺/错 `X-CSRF-Token` 时应与 `/api/user/llm/config` 一致返回 **403 `CSRF 校验失败`**。GET 路径可不要求 CSRF，但既然同一路由接受 POST 且写库，必须在处理 POST 前校验（或拆成独立的 GET-only 路由 + 受 CSRF 保护的 POST 路由）。

**证据要点**：`no csrf: 200` 且响应体里 `"user_id":16`（属主）说明**已按当前会话写库**；紧邻对照写端点 `no csrf: 403`。

**守卫为何没抓到**：现有 CSRF 用例（`test_mu1_auth.py` 的 `test_me_csrf_enables_write_after_page_refresh` 等）只对 `/api/auth/password`（或 user/llm）验证 CSRF，**从未对 `/api/predict` 断言"无 CSRF → 403"**；`test_llm_failfast.py:196` 直接 `client.post("/api/predict?...")` 不带 CSRF 且断言 200/503，等于把"predict 不校验 CSRF"固化成了通过基线。

**建议修复**：在 `predict()` 入口对 POST（或凡 `regenerate=True` / 写库路径）调用 `api_app._csrf_ok`/`auth.require_csrf`；或把写逻辑收敛到受 CSRF 的 POST 路由。

**建议回归用例**（新增 `tests/test_v36_csrf_all_writes.py`，参数化遍历路由表里所有 `methods ∩ {POST,PUT,DELETE,PATCH}` 的 `/api/*`）：
```python
@pytest.mark.parametrize("path,method", write_routes)   # 从 app.routes 自动枚举
def test_write_endpoints_require_csrf(logged_in_client, path, method):
    r = logged_in_client.request(method, path)          # 不带 X-CSRF-Token
    assert r.status_code == 403 and "CSRF" in r.json().get("error","")
```
这样新增写端点忘记接 CSRF 会立刻红，而不是等黑盒发现。

这说明"奖金/概率"这一最高风险的数值面，保护主要来自一条**昂贵且已过期**的指纹锁（P1-1），而非就地、快速、聚焦的单测。建议为 `portfolio_expected_value` 的每个返回字段（`ev_ratio/ev_ratio_sixth/prize_prob_by_level/blue_hit_prob/…`）补解析式断言。

### P2-4 `n_tickets=0` 语义空转（`actual=5`、`shortfall_reason=null`）

即 P1-2 的一个子问题：请求 0 注却返回 5 注且不说明，属"静默改写请求"。修复 P1-2 时用 `ge=1` 直接拒绝即可消除。

### P2-5 `test_qa_source_assert_meta` 的 B 类基线守卫长期无强制力

`test_external_file_string_assertions_do_not_grow` 只 `assert total <= B_BASELINE`（防增），低于基线时**不红**；下游 `test_b_baseline_should_be_lowered_to_match_reality` 只 `pytest.xfail` 提示。结果：代码删了、基线不降 → 守卫长期虚高绿灯。建议把"基线漂移"升级为 CI 周期任务报警（非阻断），或在 PR 模板里强制勾选同步。
