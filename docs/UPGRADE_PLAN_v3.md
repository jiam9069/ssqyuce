# 双色球预测系统 v3.0 升级方案（U1–U7 已于 v1.0.0 全量交付）

> 针对用户提出的两大痛点：
> 1. **界面功能太乱，需要简洁明了**；
> 2. **命中率/中奖率太低，大模型作用不明显，需进一步改善**。

基于对本地运行实例（Docker `ssq-predictor`，v0.9.0/M5.1，3510 期数据，下一期 2026114 预测已生成）的实测与代码研读，给出以下分级、可落地的升级路线。

---

## 〇、现状诊断（实测证据）

### 痛点 1：界面"太乱"——根因

当前前端是 **7 个并列 Tab 的"仪表盘工作台"**：预测中心 / 数据分析 / 规律研究 / 历史回放 / 评估报告 / 数据管理 / 设置。
其中**数据分析一个 Tab 就堆了 5 张卡片、20+ 张图表**（红球热力3模式、蓝球面板+轨迹、4 张走势图、8 张分布直方图、遗漏散点+分组）；**规律研究 Tab** 又展示 35 条规律回测表 + 4 个操作按钮 + 多选对比；**评估报告 Tab** 再拆 5 个子页。**每张票卡还折叠展开 4 段文本**（理由/规律引用/依据/反证/结构分）。

**问题**：信息密度过高，主次不分。用户打开页面被"统计数据 + 研究证据 + 回测结果"淹没，而**最核心的"买哪注"反而淹没在大量研究型信息中**。这是典型的"从研究者视角"设计的 UI，而非"从彩民/使用者视角"。

### 痛点 2：命中率低 + LLM 作用不明显——实测数据

在线累计评估（`/api/eval/cumulative`，真实开奖对照）各方法 KPI：

| 方法 | 期数 | 红球命中均值 | 蓝球命中率 | ≥五等奖率 | ROI |
|---|---|---|---|---|---|
| stat:markov | 12 | **1.565** | **8.7%** | **8.7%** | -78% |
| llm:glm-5.3-flash | 1 | 1.3 | 20% | 20% | -50% |
| llm:qwen3.8-flash | 2 | 1.2 | 0% | 0% | -100% |
| stat:freq | 14 | 1.115 | 3.8% | 3.8% | -90% |
| stat:bayes | 12 | 1.087 | 4.3% | 4.3% | -89% |
| stat:omission | 14 | 0.857 | 3.6% | 3.6% | -91% |
| **llm:deepseek-v4-flash** | 3 | **1.0** | **0%** | **4%** | -80% |
| uniform（随机） | 13 | 1.0 | 0% | 0% | -100% |

**结论（与用户判断一致）**：
1. **LLM 通道并未提升命中**，`deepseek-v4-flash` 的红球命中(1.0)甚至低于最好的统计方法 `markov`(1.565)，蓝球命中为 0%。
2. **最好的方法反而是统计模型 `markov`**。这与"双色球独立随机、无规律可循"的理论一致——LLM 的"观察→选号"本质上是在随机噪音上做模式匹配，理论上不可能稳定超过随机。
3. 所有方法 ROI 均为负（-78%~-100%），因为**蓝球命中率都远低于 1/16=6.25% 的理论值**，而五等奖/六等奖几乎全靠蓝球。

> ⚠️ **诚实前提**：双色球是独立随机事件，**任何升级都不可能稳定地"提高中奖率"超过数学期望**。因此本方案对痛点 2 的目标必须是可量化的、诚实的：
> - **短期**：把蓝球命中率拉回随机基线（≥6%）——这是**唯一有确定性改进空间**的指标（当前 LLM 蓝球 0%、统计模型 3.5-4.3%，均低于理论 6.25%）。
> - **结构性**：提升"5注/10注组合的总体命中覆盖"（利用彩票复式/胆拖的数学特性），而非单注命中。
> - **方法层面**：让 LLM 的作用从"猜测号码"转为"在结构约束下做组合优化"，并**让系统自适应地给无效方法降权**。

## 二、U1：界面重构 —— "极简预测首页"

### 目标
用户**第一眼**看到的就是**该买什么**，其它一切收进"更多"。

### 方案

**1. 首页改为"单屏预测卡"（PWA 友好）**

```
┌─────────────────────────────────────────┐
│  双色球  第 2026114 期        [开奖日]   │
│  ⏰ 距开奖 2 天 13:00                     │
├─────────────────────────────────────────┤
│  推荐号码  (10 注)          [复制全部]   │
│  ┌─第1注 红 02 07 13 19 26 32 蓝 05 ──┐ │
│  │  匹配度 ★★★★☆  组合结构：均衡      │ │
│  └───────────────────────────────────┘ │
│  ... (默认只展开第1注，其余折叠)        │
├─────────────────────────────────────────┤
│  我的号码诊断  [输入 6+1 → 立即诊断]     │
├─────────────────────────────────────────┤
│  [只看数据] [回放记录] [规律研究]       │  ← 次级入口，默认收起
└─────────────────────────────────────────┘
```

**2. 具体改动**
- **7 Tab → 2 层导航**：
  - 主层级仅 2 项：**「🎯 本期推荐」**（默认首页）+ **「📂 更多」**（展开数据分析/规律研究/回放/评估/设置 的抽屉式二级导航）。
  - 把"评估报告/数据管理/设置"这类**低频运维功能**降级为抽屉底部的"⚙️ 系统"入口，不再占据主导航。
- **票卡默认折叠**：只显示号码球 + 一句话"结构小结"；理由/依据/规律引用**点击才展开**（当前是全部平铺显示）。
- **去掉统计噪音**：预测卡不再默认展示置信度条、结构分、反证等研究者信息；改为一个**可读的匹配度星级** + 一句话结论。
- **数据分析/规律研究保留**（对有研究需求的用户仍有价值），但**入口弱化、层级加深**，不作为默认首页。
- **设置页并入抽屉**，且把"LLM开关/注数"等高频项提炼为首页右上角的小齿轮浮层。

**3. 交付物**
- `web/index.html` 重排 DOM 层级；`web/static/app.js` 增加 `renderHome()` 极简渲染路径；`style.css` 增加"卡片折叠 + 抽屉"样式。
- 复用现有 API（`/api/predictions/last`），**不改后端**即可上线。

## 三、U2：蓝球专项优化 —— 最确定的命中率杠杆

### 为什么优先蓝球
五等奖（红中3+蓝）和六等奖（仅中蓝球）**都只靠蓝球**。当前：
- LLM 蓝球命中率 **0%**（deepseek-v4-flash / qwen3.8-flash），统计模型 **3.5~4.3%**，**全部低于理论随机 6.25%**。
- 意味着系统**在蓝球这个"最容易中"的维度上是明显失分的**——这是**有确定改进空间**的，因为随机不选蓝球都能有 6.25%。

### 方案
**1. 蓝球单独建模 + 专门采样（代码级修复）**

现状问题：`engine.py` 中蓝球与红球共享同一个 `_brier_blend` 的 Brier 权重融合，且最终 `picked` 阶段**蓝球分散上限是 `max(2, n//5)`**（10注时同一蓝球最多 2 注）。这导致**蓝球覆盖面不足**（10 注最多覆盖 5 个蓝球，理论只覆盖 5/16=31%）。

改动：
- **蓝球独立模型池**：不再让 LLM/统计模型"随手"给蓝球，而是单独跑一个 `blue_specialist()`：基于历史蓝球频率 + 遗漏分布 + 最近 N 期轨迹，输出 16 维蓝球概率。
- **蓝球覆盖优先**：`picked` 阶段改为**保证 10 注尽量覆盖 10 个不同蓝球**（除非候选池不足），把单期蓝球覆盖从 ~5 提升到 ~10。**单期蓝球中奖期望从 ~31% 升到 ~62%（理论值）**——这是可量化的、正的、确定的改进。

**2. 用随机基线校准蓝球**
- 在 `/api/predict` 前加一个**蓝球内部校验**：若模型蓝球命中率长期（近60期）显著低于 6.25%，则该期蓝球**回退为 16 个均匀随机**（保证至少 6.25% 期望），而不是被模型"带偏"。

**3. 复式 / 胆拖投注模式（针对"中奖率"的本质改善）**
- 新增投注模式选择：**单式（当前）** / **蓝球复式**（如红 6 个固定 + 蓝 5 个 = 5 注，中蓝球概率升到 5/16=31%）/ **红胆拖**。
- 前端首页提供一键切换，后端 `engine.py` 支持按胆拖/复式规则展开多注。
- 这是**合法且符合彩票规则**的结构性手段：把"10 注彼此独立的低概率"变成"围绕少数核心号的覆盖式投注"，**命中（哪怕小奖）的用户体感显著提升**。

## 四、U3：方法自适应降权 + LLM 角色重定位

### 现状问题
`_brier_blend()` 虽按滚动 Brier 加权，但**只在生成候选时**起作用，且**对"整条方法通道"没有开关**。实测 LLM（deepseek）红球命中 1.0 < markov 1.565，却仍以相同权重参与融合并输出 Top10。

### 方案
**1. 方法级在线降权（A/B 已具备，补上"自动关闭"）**
- M4.2 已有 `LOTT_METHODS` 方法开关（production 模式）。升级为**自动降权**：
  - 每期开奖后在线对照（现有 `/api/eval/online`）更新各方法累计 Brier/命中。
  - **连续 K 期（如 20 期）命中显著低于随机基线（paired wilcoxon）的方法，自动降权 50% 或移出候选池**，只在"研究模式"保留对比。
  - 由"人工 A/B"升级为"**自适应的 production 策略**"，把真正有效的（如 markov）自动拔高。
- **诚实边界**：保留"研究模式"（`LOTT_METHOD_MODE=research`）展示全部方法对比，不删除任何方法。

**2. LLM 角色重定位 —— 从"猜号码"改为"组合优化 + 生成理由"**

让 LLM 去做它真正擅长、且不违背随机的两件事：
- **组合结构优化**：给定统计模型/ML 的概率向量，LLM 不直接报"红球 2 7 13..."，而是**在硬约束下优化覆盖**（和值/三区/奇偶/跨度均衡、蓝球分散、连号/同尾控制），产出"结构上更像真实开奖形态"的组合。
- **理由生成与可解释**：LLM 负责把每一注的"为什么这样组"转成自然语言，给用户提供**决策信心与教育**（而非虚假的预测能力）。
- **调用链调整**：`observations→tickets` 两步中，把 `tickets_prompt` 的输入从"让它自由选号"改为"给定 33/16 维概率分布 + 硬约束集，让 LLM 只做满足约束的组合采样 + 排序"。**号码本身由统计/ML 模型给出概率，LLM 不再越权猜测。**

**3. 蓝球交给专用模型，不交给 LLM**
- 结合 U2，蓝球由 `blue_specialist()` 决定，LLM 不再生成蓝球（当前 LLM 蓝球 0% 命中即为此改动依据）。

## 五、U4：组合命中覆盖优化（数学层面）

### 方案
- **子集覆盖**：彩票的本质是"在 33 选 6 空间里，用有限注覆盖尽可能多的命中"。
  实现一个**覆盖优化器**：给定 N 注预算，选择 N 注使"至少命中 r 个红球"的覆盖最大化（近似贪心 + 退火），并与当前"逐注独立采样"做离线对比。
- **胆拖复用核心号**：把高概率红球（模型概率 top）作为"胆"，围绕它拖出多注，使**若胆命中则多注同时命中**，提升中奖体感。
- **蓝球复式**（同 U2）组合使用。

> 这个方向有真实数学依据（覆盖设计 / 组合优化），能让用户"中一次小奖"的**期望覆盖**最大化——虽然单注期望仍为负，但**用户实际命中体验**显著改善，直击痛点2的"体感"。

## 六、U5：界面 —— 单注复盘 + "跟我买"

- **首页"历史战绩"卡片**：显示系统近 N 期的红球命中均值/蓝球命中/最好奖级/累计奖金（已有 `/api/eval/cumulative` 数据），**用诚实数字说明系统表现**，建立信任而非夸大。
- **"跟我买"一键**：从推荐注里挑出"蓝球覆盖最优 + 组合最均衡"的一组（如 5 注），一键复制，降低用户决策成本。
- **中奖回执**：开奖后首页自动显示"上期你复制的注中了没/中了几块"，形成"选号→开奖→对奖"闭环。

## 八、诚实的边界说明

必须对用户和系统一致强调：
- **双色球是独立随机事件**，任何方法（含 LLM）**都无法稳定超过随机基线**——这是数学事实，现有 3210 触发点回测 + 在线对照均已实证。
- 本方案对"命中率"的改进是**确定性的、结构性的**：
  1. 把**蓝球命中拉回甚至超过随机 6.25%**（当前系统性失分 → 修复）；
  2. 用**覆盖/复式/胆拖**提升"用户实际中奖体验"（数学上可量化）；
  3. 用**自适应降权**让系统自动聚焦真正有效的统计方法（如 markov），**移除拖累整体的无效 LLM 通道**。
- **不承诺也不实现任何"提高中奖概率"的魔法**——那既不可能也不该做。升级的价值在于：**让界面更易用、让系统更诚实、让每一分钱花在数学上更合理的地方。**

### ✅ U7：LLM 实际生成注数模式（2026-10-06 追加）

**问题**：1 轮 LLM 实际产出 4 注、请求 10 注时，引擎把 LLM 候选与统计/ML 候选混在一起，
按"蓝球覆盖优先"补齐到 10 注——用户看到 10 注，但**只有 4 注真正来自 LLM 推理**，口径不一致。

**改动**（开关 `LOTT_LLM_ONLY_OUTPUT`，默认 `1`）：
- `engine.predict_next`：LLM 产出候选且为 single/非 coverage 模式时，最终注数 = LLM **实际产出注数**，
  按置信度降序、最多保留 `LOTT_N_TICKETS`（上限），但**不补齐**；不走 `_pick_blue_coverage`
  （该函数在候选池小于注数时会重复追加同一注）。
- 响应新增 `llm_only_output`；`shortfall_reason` 用 `llm_only_actual_count` 区分"按设计不补齐"与"候选池耗尽"。
- `/api/predict` 缓存路径同步回填 `actual_tickets/requested_tickets/shortfall_reason/llm_only_output`；
  前端状态栏显示真实注数（如"4 注（按大模型实际产出，未补齐）"）。
- 纯统计模式、coverage / 蓝球复式 / 红胆拖模式行为不变；`LOTT_LLM_ONLY_OUTPUT=0` 恢复旧补齐行为。

**顺带修复**：`/api/predict` 缓存路径 `llm_used` 判断 `t["method"] == "llm"` → `startswith("llm:")`
（原判断恒为 False，因为实际 method 是 `llm:模型名`）。
